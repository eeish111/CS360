My CS 360 Portfolio Project was a Weight Tracker Application (Mobile App) designed to help users track their daily weight, set goals based on that tracked weight, and see their overall progress toward meeting that goal.

My main objective in building the application was to provide users with a very straightforward and simple method for entering and tracking their daily weight without including many "extra" features that would have made the application much more complex than necessary. As well as tracking users' daily weights, the application allowed users to create accounts and log-in to access their own data, store that data persistently across sessions, and optionally receive an SMS notification when reaching a user-defined goal weight.

To implement all of these requirements I needed to build several different screens for the application. These were a Login/Sign-Up Screen, a Weight Entry/View/Edit/Delete Screen, and a permissions screen asking for the right to send SMS messages.

The Weight Entry Screen is where users enter new weight values, review previously entered values, edit existing values, delete old values, and are shown their current and desired weights. In order to simplify usage I placed clear label names above input fields, used identical-looking buttons with descriptive name tags, and positioned the most relevant information (i.e., current weight) at the top of the screen. Additionally, the option to receive SMS notifications is completely optional – i.e., users may choose to enable this feature but will be able to use the rest of the application regardless.

As I worked on the actual implementation of the application's logic and code, I took the approach of completing one piece at a time. Therefore, I started with the UI (User Interface), followed by linking each element of the UI to its corresponding Java code and SQLite database. A helper class called DatabaseHelper was used to encapsulate all database-related operations (e.g., creating users; adding new weight entries; editing existing entries; deleting old entries; etc.) into a single location. Working on one portion of the project at a time enabled me to test each feature individually and find bugs quickly. When doing future projects, I plan to take advantage of this same methodology – work on and test each individual component separately prior to combining multiple parts into a larger application.

Testing was accomplished by using the Android emulator. I thoroughly tested logging in/log-out, creating/deleting/editing saving weights, modifying target weights, opening/closing the application, checking persistence of data through closure/opening of the application and testing both success and failure paths of requesting SMS permission. Testing in this manner was important since certain issues didn't become apparent until running the application. For example, elements within layouts failed to appear where I anticipated they would or activities weren't correctly identified in the AndroidManifest.xml file.

One area where I had to innovate was in handling the SMS permissions and making sure users were not repeatedly asked the same question every time they logged in. I used SharedPreferences to remember whether a user had already completed the SMS setup while still giving them the option to return to SMS settings later. This helped make the application feel more complete and user-friendly.

The component I feel most successful with was the database and weight tracking system. I was able to connect the UI to SQLite so users could create, view, edit, and delete weight entries while keeping their data stored between sessions. This part of the project helped demonstrate my understanding of connecting user input, Java code, and persistent data storage into one working mobile application.
